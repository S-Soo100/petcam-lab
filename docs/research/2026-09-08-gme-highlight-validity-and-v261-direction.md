## 3. 현재 기능의 유효성

실제 SQL은 `visible_sec > 0`인 run에서 활동시간 10초 이상 **또는** 최장 moving 구간 5초 이상이면 O야.
사람 verdict가 있으면 그 값이 우선이고, exact GME run이 없으면 pending이야. X와 pending은 달라.
규칙 개수 제한 없음, 한 영상 한 사람 확정, 비-blind 검수, VLM 호출 없음은 그대로 유지해.

| 측면 | 판단 | 이유 |
|---|---|---|
| 운영 구조 | 유효 | 숫자 근거·규칙 버전·사람 확정 스냅샷이 있고 수정 가능해 |
| 비용 | 현재 방식 유지 적합 | 이미 생산하는 GME run을 SQL로 읽으므로 추가 VLM 호출이 없어 |
| 활동 장면 선별 | 검증할 가치 있음 | 오래/연속으로 움직인 영상이라는 명확한 기준이 있어 |
| 재미·특별한 행동 포착 | 미검증 | 짧은 점프·머리 움직임은 X, 긴 평범한 이동은 O일 수 있어 |
| 움직임 정확성 | 개선 필요 | 정지 게코의 bbox 흔들림이 활동시간을 부풀리는 기존 감사 사례가 있어 |
| 운영 분포 | 정확도 근거로 사용 불가 | 과거 3,275개에서 O 약 15%는 선별량이지 정답률이 아니야 |

## 4. 지금 먼저 해결할 세 가지

### 4.1 앱·웹의 GME 버전 고정

`backend/routers/highlights.py::_resolve_gme_contract`는 env가 빠지면 전체 `gme_runs` 중 최신 ok run의
algorithm/detector를 선택해. 2.6.1 shadow가 새 run을 쓰면 미설정 API가 이를 따라갈 수 있어.
현재 production env가 빠졌다는 뜻은 아니고, 코드에 존재하는 조건부 위험이야.

지금 할 운영 확인은 API와 웹의 schema/algorithm/detector가 같은 승인값인지 확인하는 거야.
구현 개선은 production에서 자동 최신값 fallback을 없애고 명시한 active 계약만 읽게 하는 거야.
설정 오류는 구성 오류로 처리하고, 해당 계약의 run 부재만 pending으로 표시해.

### 4.2 유지율을 분해해서 보기

현행 `fn_highlight_rule_stats`는 규칙 버전·카메라로 묶고 최초 verdict만 집계해.
같은 규칙 아래 v2.6/v2.6.1이 섞이면 검출기 효과가 가려지고 owner 정정도 최종 품질에 반영되지 않아.

기존 최초 유지율은 보존하고 별도 평가 조회에서 `rule_version × detector_identity × algorithm_version
× camera × activity_day`를 구분해. 당시 run과 규칙으로 판정을 복원하고, 최신 유효 사람 verdict를
비교 대상으로 써. pending, 정정, 표본 수를 각각 표시해.

| 지표 | 계산·용도 |
|---|---|
| 자동 O 수용률 | O→O / (O→O + O→X): 추천을 열었을 때 쓸 만한 비율 |
| 자동 X의 놓침률 | X→O / (X→O + X→X): 제외 영상에 좋은 장면이 얼마나 남는지 |
| 사람 O 회수율 | O→O / (O→O + X→O): 대표 표본에서만 전체 회수율로 해석 |
| 기술적 오추천 | O→X 중 오검출·미관측·카메라 흔들림 사유, 사유 미입력 별도 |
| 선호 불일치 | 실제 게코는 있으나 하이라이트 아님·짧음 등의 사유 |
| 처리 커버리지 | 적격 영상 중 exact run의 decided/pending/failed 비율 |

최신 목록이나 O만 검수하면 선택 편향이 생겨. 카메라별 닫힌 밤에서 O와 X를 모두 무작위로 뽑아
기존 단독 검수 화면으로 평가해. 표본 배분이 실제 분포와 다르면 모집단 비중으로 가중하고,
단순 합산 회수율은 보고하지 않아. 사람 교차검증을 복원하지 않아.

첫 운영 점검의 제안 규모는 카메라별 3밤 이상, O 30개·X 30개야. 부족하면 개수를 채웠다고 하지
않고 실제 n을 보고해. 이는 문제 발견용 규모이며 일반화 성능 인증은 아니야.
이미 검수한 사람 답은 재작성하지 않아. 옛 3-class GT 301건도 O/X로 변환하지 않아.

### 4.3 shadow 트리거를 독립 기여로 평가

현재 `frequent_bursts`와 `early_action`은 구현돼 있지만 off야. 새 트리거가 맞은 전체 영상의
수용률보다 **기존 규칙은 X인데 새 트리거만 O인 영상**의 사람 판정이 중요해.
기존 O와 겹친 성공을 새 트리거 성과로 세지 않아. on/off 한 번에 하나만 바꿔.

## 5. 고도화 대안과 우선순위

| 대안 | 현재 가능성·효과 | 결정 제안 |
|---|---|---|
| 숫자 규칙 유지 + 평가·버전 고정 | 기존 원장으로 가능, 원인 분리가 쉬움 | 지금 우선 |
| 궤적 기반 짧은 큰 이동 추가 | artifact에서 파생 가능하지만 새 추출·검증이 필요 | 2.6.1 검증 뒤 첫 확장 |
| 의미 행동/VLM·복합 추천 모델 | 현재 owner 범위 밖이고 검증·호출 비용이 늘어남 | 이번에는 추진 안 함 |

고도화 순서는 다음처럼 잡아.

1. **규칙 v0 유지:** 10초/5초를 고정하고 O→X·X→O 원인부터 모아.
2. **짧지만 큰 실제 이동:** 안정된 동일 track 안에서 순변위·이동 범위를 구해 `wide_travel` 후보를
   shadow로 비교해. track 단절·카메라 이동·검출기 변경을 가로질러 변위를 합치지 않아.
   화면 대비 좌표는 실제 cm가 아니야. 카메라별 평가 없이 공통 임계값을 선언하지 않아.
3. **반복 짧은 움직임:** `frequent_bursts`는 jitter가 구간 수를 늘리므로 엔진 안정화 후 판단해.
4. **시작 직후 움직임:** `early_action`은 영상이 일찍 시작됐다는 뜻일 뿐 감상 가치 근거가 약해.
   단독 자동 O 트리거로 켜지 말고 기록된 추가 포착 효과부터 봐.

`fast_dash`의 단일 프레임 최대속도와 bbox 면적비는 박스 튐·가림에도 커지므로 후순위야.
2마리 동시 검출, 장소 체류만으로 먹기/마시기 추정, 카메라별 상위 백분위 자동 O,
자동 사건 묶기는 이번 확장안에서 제외해. 기존 T0/T1 실패 조건을 해소했다는 증거가 없어.
`guards`는 현재 SQL이 읽지 않으므로 params를 넣는 것만으로 품질 가드가 켜지지 않아.
오검출을 감추려고 하이라이트 임계값을 올리거나 임의 가드를 활성화하지 않아.

## 6. v2.6.1 학습 후 적용 순서

v2.6.1은 YOLO 게코 검출기야. 움직임 계산 algorithm, 하이라이트 rule은 서로 다른 버전이야.
학습 종료를 하이라이트 자동 승격 조건으로 쓰지 않아.

1. **기존 학습 계약 완료:** warm-start/clean-reference 3 seed씩, baseline 포함 validation 7회,
   checkpoint·threshold·NMS freeze, fixed regression 순서를 유지해. 계획의 precision≥0.80,
   recall≥0.90, specificity≥0.90, camera-night 최소 recall≥0.85 및 회귀 조건은 검출기 기준이야.
   이 통과가 하이라이트 정확도 80%라는 뜻은 아니야.
2. **봉인 평가 경계 유지:** 현재 계획에서 future holdout 300클립 평가와 production/shadow 채택은
   별도 계획·승인이야. 학습 완료 뒤 이 절차를 확정하고 수행해. 하이라이트 튜닝 표본으로 먼저 열지 않아.
3. **같은 영상으로 비교:** v2.6 + 현재 algorithm + rule v0를 A, v2.6.1 + 같은 algorithm + rule v0를 B로
   두고 run을 분리해. 다른 영상/다른 밤 평균만 비교하면 환경 변화가 모델 효과처럼 보여.
4. **활동시간·하이라이트 함께 확인:** 정지 jitter 사례, 실제 느린 이동 보존 사례, 독립 일반 표본을
   분리해 봐. 활동시간 감소가 오검출 감소인지 실제 움직임 누락인지 사람 근거와 대조해.
   O→X, X→O 전환표에 사람 verdict를 붙여 좋아진 전환과 나빠진 전환을 각각 세어.
5. **필요한 경우 algorithm 개선은 다음 축:** detector만 바꿔도 jitter가 남으면 별도 jitter 스펙의
   algorithm 후보를 B와 비교해. detector·algorithm·규칙을 동시에 바꾸지 않아.
6. **기술·제품 기준을 모두 충족할 때 전환:** 기술적 오추천 감소, 자동 O 수용률 개선/유지,
   사람 O 회수율과 카메라별 결과의 허용 손실, pending/처리 지연을 본다. 허용 손실 숫자는
   첫 baseline을 본 뒤 후보 결과를 열기 전에 평가 계획에 고정해. 결과를 보고 합격선을 바꾸지 않아.
7. **전환 전 coverage 확보:** 앱 조회 대상 기간에 새 exact run이 얼마나 있는지 계산해.
   전역 identity만 먼저 바꾸면 옛 영상이 pending이 되어 피드가 줄 수 있어. 승인된 조회 기간을
   새 버전으로 준비하고 웹·API를 같은 계약으로 바꿔. 필요 범위를 넘는 전량 재분석은 별도 판단해.
8. **전환 smoke·복귀:** 알려진 human O/X와 rule O/X, pending, 페이지네이션을 동일 clip으로
   웹·앱에서 확인해. 오추천/누락/서비스 오류 기준 초과 시 옛 detector·algorithm·rule 계약으로
   복귀해. run과 사람 verdict는 삭제·덮어쓰기하지 않아.

관찰 기간 제안은 전환 후 닫힌 3밤이야. 중대한 오류는 기간 종료를 기다리지 않고 복귀해.
새 검출기를 켠 뒤에야 규칙 10초/5초 주변의 소수 후보를 비교하고, 마지막에 새 트리거를 검토해.
런북의 앱 100건 페이지네이션 한계도 전환 점검 대상이야. 미노출을 검출기 누락으로 오인하면 안 돼.

## 7. 유저 체험과 완료 기준

`[화면]` 아침에 자동 O 영상과 선정 이유를 봐 → `[조작]` 한 영상을 재생해 →
`[반응]` 실제 움직임을 확인하고 검수 화면에서 O 또는 X를 확정해 →
`[감정]` 왜 뽑혔는지 납득하고, 잘못 뽑힌 영상은 고칠 수 있어.

분석 대기는 X로 설명하지 않고, 새 검출기로 바꿔도 사람이 확정한 영상은 그대로 남아야 해.
기존 라벨링의 움직임 마커·점프 기능은 재사용해. 구간 자동 절단·대표 사건 병합은 추가하지 않아.

이 기획의 다음 실행 단위는 **읽기 전용 baseline 집계 + 버전 설정 감사**야.
산출물은 카메라·계약별 표본 수/수용률/놓침률/사유/커버리지 표, 후보 비교의 고정 조건,
전환할 exact 계약 및 복귀 절차야. 현재 단계의 결론은 '구조 타당, 제품 품질 실측 필요'야.
