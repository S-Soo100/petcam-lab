# 라벨링 웹 권한별 정보구조 재설계

**상태:** 사용자 승인

**작성일:** 2026-07-24

**대상:** `petcam-lab/web` 라벨링 웹

**선행:** 이중 블라인드 라벨링 preview canary 준비 완료

## 1. 목표

현재 라벨링 웹은 큐·내 라벨·라우터 리뷰·튜토리얼·격리함·불일치 검수·그룹 배정·팀원 관리가
한 상단 메뉴에 함께 노출된다. 기능이 늘면서 사용자가 자신의 역할과 오늘 해야 할 일을 구분하기
어려워졌다.

이번 설계의 목표는 로그인한 사용자의 권한과 업무에 맞춰 **서로 다른 전용 홈과 세 개의 핵심
메뉴만 제공**하는 것이다.

- 라벨러는 오늘 작업·자신의 기록·과거 영상 확인에만 집중한다.
- Owner는 운영 현황·불일치 검수·팀 관리에 집중한다.
- 미승인 사용자는 신청·승인 상태와 튜토리얼만 본다.
- 연구·진단 기능은 일반 업무 흐름에서 분리한다.

## 2. 설계 원칙

1. **역할 우선:** 하나의 공통 메뉴를 숨기고 보이는 방식이 아니라 역할마다 명확한 홈을 제공한다.
2. **오늘 할 일 우선:** 첫 화면은 기능 목록이 아니라 사용자가 지금 처리해야 할 업무를 보여준다.
3. **Blind 불변:** 다른 라벨러의 제출과 확정 전 라벨은 어떤 우회 경로에서도 노출하지 않는다.
4. **읽기와 쓰기 분리:** 공용 영상 보관함은 탐색·재생 전용이며 라벨 제출은 작업 화면에서만 한다.
5. **출처 명시:** 과거 라벨과 새 이중 블라인드 최종 라벨을 같은 신뢰도로 위장하지 않는다.
6. **작은 화면 우선:** 320px부터 메뉴·숫자·버튼이 잘리거나 두 줄로 내려앉지 않아야 한다.

## 3. 역할 정의

### 3.1 승인 라벨러

`public.labelers`에 존재하고 승인된 `labeler_applications`를 가진 사용자다.

핵심 메뉴는 세 개다.

1. `오늘 작업`
2. `내 기록`
3. `영상 보기`

팀 관리·불일치 검수·연구 도구는 접근할 수 없다.

### 3.2 Owner

제품 Owner 권한을 가진 사용자다.

핵심 메뉴는 세 개다.

1. `운영 현황`
2. `불일치 검수`
3. `팀 관리`

Owner가 직접 라벨링할 때는 네 번째 메뉴를 추가하지 않고 `운영 현황` 상단의 `직접 라벨링`
보조 버튼으로 진입한다.

Owner가 동시에 승인 라벨러 레코드를 가지고 있어도 기본 역할은 Owner다. 로그인 직후와 공통
`/labeling` 진입에서는 Owner 홈을 우선하고, 라벨러 작업 화면은 `직접 라벨링` 버튼으로만 명시적으로
전환한다. 역할 판정 순서는 `Owner → 승인 라벨러 → 미승인 사용자`로 고정한다.

### 3.3 미승인 사용자

로그인은 했지만 승인된 라벨러도 Owner도 아닌 사용자다. 공통 메뉴를 표시하지 않고 단일 참여
화면만 제공한다.

- 신청 전·승인 대기·반려 상태
- 라벨러 신청 또는 튜토리얼 계속하기
- 비밀번호 변경
- 로그아웃

영상·팀·라벨링 API와 화면에는 접근할 수 없다.

## 4. 사용자 체험 흐름

### 4.1 라벨러

`[화면] 오늘 할 일과 남은 건수`

→ `[조작] 첫 영상을 선택`

→ `[반응] blind 상세에서 판정·구간·행동을 제출`

→ `[반응] 다음 미제출 영상 또는 완료 화면`

→ `[감정] 다른 기능을 찾지 않아도 오늘 업무가 끝났음을 알 수 있음`

`오늘 작업`의 기준일은 달력의 오늘이 아니라 **가장 최근에 닫힌 활동일**이다. 활동일 경계는 기존
계약대로 07:00 KST다. 해당 활동일을 모두 제출하면 더 오래된 미완료 활동일로 이동할 수 있다.

### 4.2 Owner

`[화면] 그룹별 제출률·미완료·불일치·Canary 현황`

→ `[조작] 불일치 건수 선택`

→ `[반응] 두 제출이 모두 끝난 충돌 건만 비교 검수`

→ `[조작] 최종 판정`

→ `[감정] 전체 영상을 다시 보지 않고 예외만 처리함`

Owner가 직접 라벨링할 때는 `운영 현황 > 직접 라벨링`으로 별도 작업 화면에 진입하고, 운영 메뉴와
라벨링 메뉴를 한 줄에 섞지 않는다.

### 4.3 미승인 사용자

`[화면] 현재 참여 상태와 다음 행동 한 가지`

→ `[조작] 신청 또는 튜토리얼 진행`

→ `[반응] 승인 전에는 보호된 업무 화면으로 이동하지 않음`

→ `[감정] 무엇을 기다리고 무엇을 해야 하는지 명확함`

## 5. 라벨러 화면

### 5.1 오늘 작업

- 가장 최근에 닫힌 활동일의 배정 영상
- 전체·완료·남은 건수
- 카메라와 촬영 시각
- 재생 가능 여부
- 제출 완료 후 같은 활동일의 다음 영상
- 활동일 완료 후 이전 미완료 활동일 진입

상대 라벨러의 제출 여부·판정·digest·GT·진행 순서는 표시하지 않는다.

### 5.2 내 기록

본인이 제출한 기록만 보여준다.

- 날짜·시간대·카메라·본인 판정 필터
- 본인이 제출한 decision·reason·GT
- 제출 시각
- 최종 합의 상태는 `확정됨·검수 중` 수준으로만 표시

상대 제출 원문과 불일치 필드는 노출하지 않는다.

### 5.3 영상 보기

모든 승인 라벨러가 사용하는 공용 읽기 전용 영상 보관함이다.

- 모든 카메라
- R2에 존재해 실제 재생 가능한 영상
- 날짜·시간대·카메라·최종 라벨·라벨 상태·라벨 출처 필터
- 날짜 및 시간 역순 탐색
- 상세 재생

여기서는 라벨을 제출·수정·보류·제외할 수 없다.

## 6. 영상 보관함 라벨 공개 계약

### 6.1 새 이중 블라인드 영상

- 합의 완료: 최종 합의 라벨 표시
- Owner 해결 완료: Owner 확정 라벨 표시
- 한 명만 제출 또는 두 명 미제출: `라벨 확정 중`
- 충돌 발생 후 Owner 미검수: `Owner 검수 중`

개별 라벨러의 답은 표시하지 않는다.

### 6.2 체계 도입 이전 영상

출처를 다음과 같이 명시한다.

- `기존 Owner 라벨`
- `기존 단일 라벨`
- `라벨 없음`

기존 단일 라벨도 승인 라벨러에게 표시하되 최종 합의 라벨과 시각적으로 구분한다.

### 6.3 Blind 재검수

과거 영상이 새 blind cohort에 편입되면 기존 사람 라벨을 일시적으로 숨기고 `라벨 재검수 중`으로
표시한다. cohort가 합의 또는 Owner 해결로 종료된 뒤 새 최종 라벨을 공개한다.

VLM·Python Evidence·Gate 판정과 다른 AI 출력은 라벨러 영상 보관함에 표시하지 않는다.

## 7. Owner 화면

### 7.1 운영 현황

- 그룹별 최근 닫힌 활동일 제출률
- 라벨러별 오늘 완료 수
- 미완료 영상 수
- 불일치·Owner 검수 대기 수
- 열린 Canary 목록과 라벨러별 완료 수
- 재생 불가·API 실패 같은 운영 오류
- `직접 라벨링` 보조 버튼
- 접힌 `연구 도구` 진입

`연구 도구`에는 기존 격리함·라우터 리뷰·실험성 진단 화면을 배치한다. 상시 핵심 메뉴로 노출하지
않는다.

### 7.2 불일치 검수

- 두 제출이 모두 끝난 conflict만 노출
- 서로 다른 필드 요약
- 두 사람의 제출 비교
- 영상 재생
- Owner 최종 판정
- 해결 완료 기록

### 7.3 팀 관리

- 사용자 신청·승인 상태
- 그룹별 두 라벨러
- 담당 카메라
- 배정 변경 이력
- Canary 생성·종료

그룹·카메라 변경은 명시적 확인 단계를 거쳐야 하고 단순 화면 진입으로 mutation이 발생하면 안 된다.

## 8. Canary 동일 링크 계약

`/labeling/blind/canary/[cohortId]`는 로그인 역할에 따라 다르게 렌더링한다.

### 라벨러

- 자기에게 배정된 canary 영상
- 본인 제출 수/전체 수
- 상대 답안·상대 제출 상태 비공개

### Owner

- cohort 이름·상태·전체 영상 수
- 두 라벨러의 이름과 각 완료 수
- awaiting·agreed·conflict·owner_resolved 수
- 라벨러에게 전달할 동일 링크 복사
- conflict 검수 진입

Owner에게도 한 사람만 제출한 개별 답안은 표시하지 않는다. 두 제출이 끝난 conflict는 기존 Owner
검수 권한으로 확인한다.

Owner도 라벨러도 아닌 사용자는 `403 forbidden`으로 차단한다.

## 9. 반응형·접근성 계약

### 9.1 화면 구간

- `320–639px`: 한 열, 하단 고정 3탭
- `640–1023px`: 내용 카드만 조건부 2열, 메뉴는 한 줄 유지
- `1024px 이상`: 220px 사이드 메뉴 + 최대 960px 본문

### 9.2 잘림 방지

- grid/flex 자식에 `min-width: 0`
- 메뉴명·숫자·주요 버튼은 `white-space: nowrap`
- 긴 카메라·사용자 이름만 말줄임 처리
- 말줄임 요소에는 전체 이름을 접근성 이름 또는 title로 제공
- 모바일 탭은 아이콘+짧은 한글 라벨
- 가로 스크롤로 메뉴를 숨기지 않음

### 9.3 검증 해상도

최소 다음 너비에서 스크린샷 회귀검사를 수행한다.

`320 / 360 / 390 / 768 / 1024 / 1440px`

각 화면에서 다음을 확인한다.

- 메뉴·버튼·진행 숫자 줄바꿈 0
- 카드·필터·영상 영역 viewport 밖 잘림 0
- 200% 브라우저 확대에서도 핵심 작업 가능
- 키보드 포커스와 접근성 이름 유지

## 10. 권한 및 보안

화면에서 메뉴를 숨기는 것은 보안 경계가 아니다. 모든 API는 서버에서 역할을 다시 확인한다.
역할에 맞지 않는 화면의 직접 URL은 역할 홈으로 안내하되, 보호 API는 redirect에 의존하지 않고
`403`으로 차단한다.

| 기능 | 라벨러 | Owner | 미승인 |
|---|---:|---:|---:|
| 오늘 작업·제출 | 본인 배정만 | 직접 라벨링 경로 | 차단 |
| 내 기록 | 본인 제출만 | 직접 라벨링 기록 | 차단 |
| 영상 보기 | 읽기 전용 전체 카메라 | 읽기 전용 전체 카메라 | 차단 |
| 최종 라벨 | 확정된 라벨만 | 확정된 라벨 | 차단 |
| 상대 제출 | 차단 | conflict 검수 시만 | 차단 |
| 운영 현황 | 차단 | 허용 | 차단 |
| 그룹·팀 변경 | 차단 | 확인 후 허용 | 차단 |
| 연구 도구 | 차단 | 허용 | 차단 |

API 응답은 allowlist mapper를 사용하고 reviewer UUID·lease token·digest·R2 key·VLM/Evidence 원문을
클라이언트 응답에 포함하지 않는다.

## 11. 오류·빈 상태

- 오늘 작업 0건: `오늘 할 라벨링을 모두 끝냈어`
- 과거 미완료 있음: `이전 활동일 작업 보기`
- 재생 불가: 해당 영상만 실패 처리하고 다음 작업 가능
- 영상 보관함 검색 결과 0건: 현재 필터와 초기화 버튼 표시
- Canary owner 접근: 현황판 표시
- Canary 비배정 라벨러: 작업이 없다는 일반 메시지, cohort 내부정보 비노출
- 만료/종료 Canary: 만료 안내와 홈 이동
- API 실패: 재시도 버튼과 오류 코드 없는 사용자 문구

### 포함

- 역할 기반 landing과 navigation
- 라벨러 3화면

- 미승인 단일 화면
- 공용 읽기 전용 영상 보관함

## 13. 수용 기준

1. 각 역할이 로그인 후 자신의 전용 홈으로 이동한다.
2. 각 역할의 기본 메뉴가 세 개를 넘지 않는다.
3. 라벨러는 상대 제출과 확정 전 라벨을 어떤 API·화면에서도 볼 수 없다.
4. 영상 보관함에서 모든 카메라의 재생 가능한 영상을 합의된 필터로 탐색할 수 있다.
5. 과거 라벨 출처가 명확히 구분된다.
6. Owner가 Canary 동일 링크에서 두 라벨러의 진행률과 상태를 확인한다.
7. 6개 검증 너비에서 잘림·메뉴 줄바꿈이 없다.
8. 기존 legacy·motion labeling·튜토리얼의 저장 payload와 GT 계약은 바뀌지 않는다.
9. 권한별 API 적대 테스트와 전체 회귀가 통과한다.
